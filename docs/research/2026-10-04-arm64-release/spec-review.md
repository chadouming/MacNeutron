Three lenses (accuracy against the code, completeness against earlier work, feasibility of the mechanisms), each re-checked by a sceptic, on the draft at `bd23622`. # REVIEW 0: verdict
The spec accounts for almost everything earlier work handed to sub-project 5, but it does not inventory what deleting the Rosetta path leaves behind. I checked it against the 18-row table in map-arm64-deliverables.md §10, which lists every place the earlier specs assign work to sub-project 5 or the launcher. Row 1 (per-game runtime choice, preflight split) is superseded by the §1 decision. Rows 2-15, 17 and 18 are covered: 2 in §3.9, 3 in §3.7, 4 in §3.5 (the helper.exe slip is corrected in §2), 5 in §3.4 step 5, 6 in §3.4 step 3, 7 in §1, 8 in §6.2 (R0), 9 in §7.2, 10 in §6.3 step 1, 11 in §5.2, 12 in §5.3, 13 in §3.8, 14 in §8.2 (L1, L2), 15 in §3.3, 17 in §7.1. Row 18 (the parts of the DXMT spec's scope and §6, the ship-base spec's scope and §13, and the ship-base acceptance's "Found on the way" that were sent to sub-project 5) is covered by the same sections. One item was dropped silently: row 16, the MacNeutron licence line the ship-base spec (§4) asked for in the licence README that ships inside wine.app. Two earlier warnings are carried in but contradicted or left unhandled: the native spec says matching processes by argv (`pkill -f`) misses Wine processes, yet §3.9 uses `pgrep -f`; and both the native and ship-base specs say a client and wineserver in different msync modes cannot mix, which §3.7 handles only within one launch. The orphan side is not inventoried:
- the Makefile `app` target and other targets;
- the CLI verbs `install-runtime`, `import-gptk` and `install-dxmt`, and how the checks will assemble a tool folder without them;
- the prerequisites `dxmt/check.sh` needs beyond the frozen tool;
- `smoke.sh`, `dxmt/tests/run.sh`, the app's Settings "Repair runtime" button and menu status line;
- the shipped and repository READMEs, which would contradict the release.

Tests are covered in one sentence ("the Rosetta tests go with their code") plus a list of new tests. That is thin but present. The README's promises to users are contradicted in many places and §7 does not plan a rewrite. Nothing found blocks the design, but several Important gaps would trip the plan or ship wrong text.

## R0.0 [Important] §3.9 step 2 (and §12 'replaced under a running game', gate L6)
PROBLEM: The guard that delays the wine.app swap while a game runs finds processes with `pgrep -f`, which matches on argv. Wine rewrites its processes' argv, so the guard sees nothing. The swap would then go ahead under a running game: new Windows processes the game starts would run the new loader against the old wineserver, and the spec itself says that combination fails. L6 can still pass if its test process keeps an argv that contains the path. The check, the two renames and a concurrent launch are also not serialised: between the check and the renames, or between the two renames, a launch can find no wine.app, or start the old loader just before the swap.
EVIDENCE: Native spec §3.3 'Lessons the design carries' (2026-10-02-macneutron-native-arm64-design.md:132): Wine rewrites a client's argv, so `pkill -f <path>` misses it, and only `wineserver -k` or killing by executable path (`lsof -t`) cleans up. wine-arm64/check.sh:46-58 says the same ('Wine rewrites argv, so `pkill -f <path>` finds nothing; the kernel knows the executable') and uses `lsof -t "$f"` on Contents/MacOS/wine and Resources/bin/wineserver. The spec's §3.9 step 2 says 'found by its path, e.g. `pgrep -f`'. The tool-file refresh was written so that 'a game launching at that moment never sees a missing launcher' (steam-bridge spec line 122), but §3.9 has a window where wine.app is missing between the two renames.
FIX: Replace step 2 with: 'If `lsof -t` on `wine.app/Contents/MacOS/wine` or `Contents/Resources/bin/wineserver` lists any process (the kernel's executable, not argv, which Wine rewrites), defer to the next start.' Take a tool-folder lock (for example `<tool>/install.lock`, also taken briefly by the launcher before preflight) around the check and both renames. Make L6's deferral case run a real Wine process (for example `wine.app/Contents/MacOS/wine` running a test program that waits), not a process whose argv contains the path.

## R0.2 [Important] §1 Goal, §9 R6, §3.1 (the `proton` stub)
PROBLEM: The goal promises play 'with no Rosetta installed', but no gate can observe that. Rosetta is installed for the whole system, so R6's fresh user account on the maintainer's Mac still has it. Steam starts tools preferring x86_64, and the tool's entry point is the `/bin/sh` `proton` stub. `/bin/sh` contains an x86_64 slice, so on this Mac it can run translated without anyone noticing. What happens on a Mac without Rosetta is untested. The §3.1 tree doesn't list the stub, and §3.11 only makes the CLI arm64-only.
EVIDENCE: `ls -d /Library/Apple/usr/libexec/oah` returns the path, and `/usr/bin/arch -x86_64 /usr/bin/true` succeeds, so Rosetta is present for every account. `lipo -archs /bin/sh` prints `x86_64 arm64e arm64e.x1`. Sources/MacNeutronCore/SteamPlayMode.swift:20-22 says Steam 'starts tools preferring x86_64, which carries through `exec`'. RuntimeInstaller.swift:54 writes `"commandline" "/proton %verb%"`, and the installed `proton` file is `#!/bin/sh` / `exec "$(dirname "$0")/bin/macneutron" launch "$@"`. Spec §2: 'a universal CLI would run translated'.
FIX: In §3.1, either point toolmanifest.vdf's commandline at the arm64-only binary directly (`"/bin/macneutron launch %verb%"`, so no universal file sits between Steam and the CLI) or keep the stub and say why. Add a gate R7 (maintainer): run R6 in a macOS 27 virtual machine (Virtualization.framework) where Rosetta was never installed. If that is out of scope, weaken §1 to 'no MacNeutron process runs translated' and check it in R6 with `ps -o pid,comm` plus `sysctl.proc_translated` per process.

## R0.8 [Minor] §3.7, §10 (msync mode across launches)

The design works in outline. The signing order is right: wine.app is signed first, then the outer app around it without re-signing wine.app. Contents/Helpers is a valid place for nested code. @loader_path in dlopen already works in this process through the existing LC_RPATH. The size figures check out against the staged bundle (1.3G; lsteamclient.dll is 57,496,064 bytes; icu.dll is 80 MB; there are 249 .a files totalling 36 MB). But seven Important gaps need fixing before planning: (1) the build identity misses the loader and Info.plist; (2) git archive leaves out the FEX and DXMT submodules and cannot archive the sparse, partial-clone lsteamclient tree; (3) nothing tests quarantine or the unstapled ticket on the wine.app copied into the tool folder; (4) the 'no Rosetta installed' goal is never tested, and Steam still starts a universal /bin/sh stub; (5) Steam's install-script redistributables are 32-bit, and the spec doesn't say how the `run` verb handles them; (6) stripping uses LLVM 15 on ARM64X images, and no automated gate ever runs the stripped wine.app; (7) build.sh's fixed output folder and its 'up to date' skip don't fit the release bundling as written. ## R1.0 [Important] §1 refinements, §5.1, §3.4, §3.9
PROBLEM: The build identity (SHA-256 of Contents/_CodeSignature/CodeResources) does not cover the main executable or Info.plist, so the spec's claim that it 'seals every file's hash and the Info.plist' is wrong. Three kinds of change would leave the identity unchanged: a change to the loader alone (loader/ code, configure link flags, patch 0001), a change to wine.entitlements alone (which only changes the loader's signature), and a change to Info.plist alone. The app would then not reinstall wine.app (§3.9), and prefix stamps would not refresh (§3.4).
EVIDENCE: `plutil -p build/wine-arm64/wine.app/Contents/_CodeSignature/CodeResources | grep -E '"(Info.plist|MacOS/[^"]*|embedded.provisionprofile)"'` matches only `"embedded.provisionprofile"` (line 1264) and `"MacOS/ntdll.so"` (line 1267). There is no entry for Info.plist or MacOS/wine, because codesign seals both through the main executable's code directory (special slots), not through CodeResources.
FIX: Make the identity the SHA-256 of the signed loader file `Contents/MacOS/wine`, or the loader's CDHash from `codesign -d -v`. Its embedded code directory hashes Info.plist, CodeResources and the entitlements, as well as the executable's own pages, so one hash covers the whole bundle. It is still cheap (54 KB). Correct the wording in §1 and §5.1, and add a unit test with two bundles that differ only in the loader.

## R1.1 [Important] §7.2, gate R5
PROBLEM: `git archive` of the applied trees does not produce the trees 'as built'. It writes submodules (gitlinks) as empty folders, so FEX's External/* and cpp-optparse, and DXMT's include/native/directx, are missing. lsteamclient's tree is a shallow `blob:none` partial clone of the whole Proton repository with a sparse checkout, so `git archive HEAD` there would try to fetch every Proton blob, including the steamworks_sdk_* folders the build deliberately leaves out. R5 would fail on the FEX_SUBMODULE_* lines, and would not notice DXMT's missing headers because SOURCE doesn't list them.
EVIDENCE: `git -C build/wine-arm64-src/fex ls-tree HEAD External/fmt` shows `160000 commit 1be298e…` (a gitlink). R5 then checks each nested tar's commit against SOURCE and each tarball's SHA-256 against its pin.

## R1.2 [Important] §3.9, §6.2 (R0), R6
